## Integration phases and acceptance gates

The bounded private snapshot may be shared after its own projection checks
pass while proof import and cost work remain visibly `OPEN`. Full cost
accounting is not a prerequisite for sharing that limited snapshot.

### 1. Exact inventory and custody — OPEN

Dependency: the retained bootstrap evidence and source packages.

Produce an inventory for M3 and K1 containing claim IDs, exact theorem names,
hypotheses, module dependencies, source hashes, operation terminal roots,
promotion roots, toolchain, Lake manifest, and the dependency-cache policy.
Identify the source boundary against which each native correspondence was
proved. Distinguish proof modules, diagnostics, obsolete admitted workbench
files, failed attempts, and executable realizations.

Acceptance: every claimed result has a traceable evidence root; imported
members have byte hashes and redistribution dispositions; the manifest names
the complete required envelope; no private correspondence, credentials, or
personal machine paths enter the projection. Missing or uncertain custody is
recorded as a blocker rather than inferred from a passing summary.

### 2. Stage the proof chain — OPEN

Dependency: Phase 1.

Stage M3's complete no-escape centered and `A = 0` chain, then K1's coefficient
identity, scalar source bridge, recurrence kernel, counted semantics, zero
branches, and coordinatewise orbit decision. Use an explicit replay envelope
or a documented pinned-source acquisition procedure. Keep historical
counterexamples and corrections visible, with successor statements linked.

Acceptance: all imported sources match the inventory; every required import
is accounted for; no obsolete admitted declaration lies in the asserted proof
boundary; theorem statements preserve their actual source hypotheses. The
staging step alone does not promote mathematical standing.

### 3. Cold replay M3 and K1 — OPEN

Dependency: Phase 2. The historical M3 r5 replay is a useful baseline, not a
substitute for this successor integration test.

Replay both chains from a fresh extraction or clean checkout with the pinned
Lean/Lake environment. Verify hashes before execution and after archive
extraction, retain exact commands and terminal records, and run the no-escape
court. State whether dependencies are rebuilt from source or realized through
the pinned cache. Preserve warnings and failures; distinguish a strict target
check from warnings in intermediate modules.

Acceptance: M3 and K1 have separate fresh `PASS` receipts bound to the candidate
tree and manifests, with no missing required check. A hash-only receipt check
must remain labelled as custody verification. Replaying the author's evidence
does not establish independent verification.

### 4. Separate formula verifier and mutations — OPEN

Dependency: the exact statement inventory in Phase 1. Implementation may run
in parallel with proof staging.

Package a standalone exact formula verifier using a separately implemented
oracle, not two calls through the same recurrence. Cover the declared finite
box and boundary cases: `A = 0`, `R = 1`, `m = 0`, generalized binomials with
negative upper arguments, mismatch support, and outside-orbit zero branches.
Retain expected refusals and counterexamples.

Acceptance: deterministic receipts state the box, oracle relationship, and
equality counts. Mutations must expose a missing sign, wrong delta, missing
power-of-two scale, ordinary-binomial substitution, and damaged support or
orbit branch. Record exact witnesses. Finite success does not prove a general
identity, and a separate local implementation is not external review.

### 5. Source and cost scope audit — OPEN

Dependency: Phases 3 and 4 for claims about the integrated realization.

Check scalar equality under its exact hypotheses separately from total joint
value equality. Identify which costs are proved, measured, transparently
counted, or excluded. Preserve the exact arithmetic vector and the exclusions
for sign changes, exponent construction, indexing, allocation, and machine
effects. State separately any justified bit-cost bound.

For a later total-cost comparison, first charge coordinate orbit comparisons
and short-circuit behavior, mismatch and active-set construction, and the
relevant consumer. A matrix-wide claim additionally requires materialization
and traversal costs. If no deployed charged consumer exists, retain that
obstruction as the result.

Acceptance: no scalar count is described as full per-cell cost or native SAT
speedup. Enumeration comparisons state their parameter regime: at fixed `R`,
`sum_{j<R} C(Q-1,j) 2^j` is polynomial in `Q`; an exponential comparison needs
an explicit joint regime. Historical sealed source copies are preserved, and
any corrected interpretation receives a revision note. Complete runtime cost,
deployment, and SAT asymptotics may remain `OPEN` in a bounded review snapshot.

### 6. Freeze the bounded private snapshot — OPEN

Dependency: the chosen snapshot scope, its custody checks, and repository
qualification. Phases 2–5 are prerequisites only for claims that rely on their
completion; an evidence-summary snapshot explicitly leaves them open.

Record a freeze receipt with the Git commit or candidate-tree identity,
manifest hashes, included claims, exclusions, checks run, platform results,
unobserved work, and known remainder. Keep the receipt outside any tree whose
hash it contains. Update the registry, generated index, and revision records
together. Run `python -B tools/qualify_repository.py` from a clean candidate
checkout; require the declared Windows and Ubuntu CI jobs for the same commit
before calling its cross-platform checks complete. Existing CI does not replay
Lean unless a successor check explicitly installs and runs that chain.

Review rights and attribution for each newly projected path. Pending public
licensing remains visible. Private staging is the only external repository
effect in scope; public visibility, release preparation, and reviewer contact
are `DEFERRED`.

Acceptance: the receipt's claim ceiling matches what the checkout actually
checks; no local-only result appears as checkout-replayed; failed or missing CI
is reported accurately; the private repository remains private. A successful
repository qualification does not establish mathematical review or novelty.

## Explicit pause and feedback boundary

After the bounded roadmap and evidence snapshot is staged, stop. Keep the
discovery loop paused while awaiting user feedback. Do not automatically begin
Phases 1–5, a persistent investigation, or an automation merely because they
are listed here. Feedback may select proof integration, cost accounting, or a
different bounded question; any successor scope must be recorded first.
