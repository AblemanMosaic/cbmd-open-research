# Revision 0.4.0 — the class-count bound, compiled as injectivity

Revision 0.3.0 compiled U1. This compiles U2, the bound on contributors to a
sum of target rows, by isolating the part of it that needs an argument.

## What the bound actually rests on

The written claim is: *for sums of target rows, contributors per owner are
bounded by the number of distinct `(block, orbit-class)` pairs.* Unpacked in
the single-block model, it is two steps.

A column contributing to a sum has a nonzero row against **some** target, so
it lies in that target's orbit, so its own orbit class is one of the classes
present among the targets. That part is bookkeeping.

The step that needs proving is that for a fixed owner, **each class holds at
most one column**. Given that, the contributors inject into the classes
present, and the bound is pigeonhole.

```lean
theorem contributor_class_injective
    (support_in_orbit : ∀ u y, Support u y → InOrbit u y)
    (coherent : ∀ y, headOf (own y) = y.head)
    (v : Owner) {u u' y z : Typ Q r}
    (hy : own y = v) (hz : own z = v)
    (sy : Support u y) (sz : Support u' z)
    (same_class : InOrbit u u') : y = z
```

Two targets in one class, two columns of one owner supported at them: the
columns coincide. Stated for a pair rather than a list, so nothing finite and
no cardinality enters — the pigeonhole step is left where it belongs, in the
reader's head, and what is compiled is the injectivity it rests on.

It needs `InOrbit` to be an equivalence, which it is: at each coordinate the
condition is that the unordered pair `{head, slot}` agrees, so `inOrbit_symm`
and `inOrbit_trans` are case analyses and depend on no axioms.

## The same two hypotheses

Nothing new is assumed. `support_in_orbit` and `coherent` are the same two
inputs as 0.3.0, and the census measures both against its own layouts.

## Evidence

The verifier now also measures the compiled statement directly, as occupancy
of the owner-by-class table:

| quantity | count |
|---|---|
| occupied owner-class cells | 96 |
| cells holding more than one column | **0** |
| largest cell | **1** |
| owners spanning two or more classes | 30 |

The last row is the anti-vacuity control. If every owner sat inside a single
class, the class-count bound would never say anything beyond "at most one",
and 0 unsound would be measuring the trivial case. Thirty owners span two or
more, so the bound is doing work where it is checked.
